THE WORKLOADS MOVING INTO CLUSTER B, AND THE NODES THEY WILL COST

In this article ❧ Platform teams write rules that fire when incoming demand passes a share of what a system already carries, so the budget moves on evidence rather than on instinct, and so nobody argues about the trigger after the fact. This problem shows how one comparison between two counts turns raw volume into a decision, and how Python can hold that rule for any future cluster.

The Problem

A platform lead set a capacity rule. If the workloads scheduled to migrate from Cluster A into Cluster B next year exceed 110% of Cluster B's current workload count, the team will add compute nodes to Cluster B. Cluster A currently runs 750 workloads. Cluster B currently runs 625 workloads.

Will the team have to add nodes to Cluster B next year?

  • a) Yes, because Cluster A is 115% larger than Cluster B.
  • b) No, because Cluster B is 105% larger than Cluster B.
  • c) Yes, because Cluster A is 120% larger than Cluster B.
  • d) Yes, because Cluster A is 111% larger than Cluster B.
Click to Reveal the Answer

Correct Answer: c) Yes, 120% ✅

Math Solution

Divide the incoming count by the current count, 750 over 625, which gives 1.20, then convert that to 120%. The result sits above the 110% trigger, so the team adds nodes.

The base in the rule is Cluster B, not Cluster A, and every reading of the result depends on that choice.

Step-by-Step Breakdown

The following sequence shows how the final amount is derived:

  1. Reference base: Cluster B runs 625 workloads today, the denominator for the comparison
  2. Trigger in absolute terms: 625 × 1.10 = 687.5 workloads
  3. Incoming volume: Cluster A runs 750 workloads, the numerator
  4. Ratio: 750 ÷ 625 = 1.20, so the incoming volume is 120% of the current load
  5. Comparison: 1.20 > 1.10, and 750 > 687.5, so both forms of the test agree
  6. Margin: 750 − 687.5 = 62.5 workloads above the trigger
  7. Decision: add compute nodes to Cluster B

Three Routes to the Same Decision

Route A, the gap route. Compare the gap between the two clusters against 10% of the base. The gap is 750 − 625 = 125 workloads. Ten percent of the base is 625 ÷ 10 = 62.5. Since 125 = 2 × 62.5, the gap equals 20% of Cluster B's load, so the incoming volume reaches 120% and clears the trigger by 10 points. Use this one in a standup, because it needs no division beyond a move of the decimal point.

Route B, the share route. Ask what share of Cluster B's current load the incoming volume represents. Write 750 = p × 625, then p = 750 ÷ 625 = 1 + 1/5 = 1.20, which is 120%. Use this one in a capacity model, where the ratio feeds a formula rather than a conversation.

Route C, the unit route. Build a percent point and count how many fit. The whole is 625, the base named in the rule, and it is smaller than 750, so the result exceeds 100% before any arithmetic runs. Split the base into 100 units, 625 ÷ 100 = 6.25 workloads per percent point, then count the units in the incoming volume, 750 ÷ 6.25 = 120 percent points. The reverse check runs the conversion the other way, 100 ÷ 625 = 0.16 percent points per workload, then 750 × 0.16 = 120. Use this one when writing the policy document, since it names the unit the threshold is measured in.

All three routes return 120% and the same decision. The team adds nodes to Cluster B. One caution on the reverse check in Route C, the factor 0.16 converts workloads into percent points, so it applies to the count of 750 and not to the result of 120.

Historical Background

Comparing a quantity against a base period is one of the oldest habits in commerce, and the twentieth century turned it into a discipline. Irving Fisher published The Making of Index Numbers in 1922, which examined how such comparisons behave and showed that competing formulas for the same question can disagree, a finding that still shapes how statistical agencies build price indexes. The same reasoning moved into operations research after the Second World War, where factory managers set reorder and expansion triggers as a share of current throughput rather than as fixed counts. Cloud capacity planning inherited that pattern intact, and a modern autoscaling policy is a threshold written against a baseline.

Python Version

The script holds the capacity rule itself, so any cluster, any incoming volume, and any threshold can be tested without rewriting the logic.

# What this does: checks if a cluster needs more compute nodes next year.
# Where it came from: a platform team adds nodes when the workloads moving in
# pass a set percent of the cluster's current load.
# The math idea: divide one count by the other, then turn it into a percent.
# You type in: the incoming workload count, the current workload count, and
# the threshold percent.
# It prints: the percent reached and whether the team adds nodes.

# This function does the math.
def capacity_check(incoming_workloads, current_workloads, threshold_percent):
    # Work out what percent the incoming count is of the current count.
    reached_percent = (incoming_workloads / current_workloads) * 100
    # Work out the count that would sit right at the threshold.
    trigger_count = current_workloads * (threshold_percent / 100)
    # Say yes only when the incoming count is above that trigger.
    needs_nodes = incoming_workloads > trigger_count
    return reached_percent, trigger_count, needs_nodes

# Tell the reader what we will figure out.
print("Let's find out if Cluster B needs more nodes next year.")

# Ask for the workloads moving in from Cluster A.
incoming_workloads = float(input("Workloads moving in from Cluster A: "))

# Ask for the workloads Cluster B runs today.
current_workloads = float(input("Workloads on Cluster B today: "))

# Ask for the percent that triggers new nodes.
threshold_percent = float(input("Threshold percent that triggers new nodes: "))

# Do the math.
reached_percent, trigger_count, needs_nodes = capacity_check(
    incoming_workloads, current_workloads, threshold_percent
)

# Show the percent with two decimals, and no decimals when it is whole.
reached_percent = round(reached_percent, 2)
reached_percent = int(reached_percent) if float(reached_percent).is_integer() else reached_percent

# Show the trigger count the same way.
trigger_count = round(trigger_count, 2)
trigger_count = int(trigger_count) if float(trigger_count).is_integer() else trigger_count

# Print the answer with words that fit the scenario.
print("Incoming volume reaches", str(reached_percent) + "% of Cluster B's current load.")
print("The trigger point sits at", trigger_count, "workloads.")

# Print the decision in plain words.
if needs_nodes:
    print("Decision: add compute nodes to Cluster B.")
else:
    print("Decision: no new nodes needed for Cluster B.")

Paste it into a Python session, type 750, then 625, then 110, and it returns 120%, a trigger point of 687.5 workloads, and the instruction to add nodes.
