THE BACKUP VOLUME FILLS UP LONG BEFORE ANYONE ORDERS MORE STORAGE

In this article ❧ Storage capacity is one of the few resources an operations team spends without ever signing an order. Every routine backup consumes a share of the same volume, and the team notices the cost only when a write fails and the recovery plan stops working. This problem shows how a repeated share of a fixed capacity turns into a planning figure, and how the arithmetic behind that figure can be named property by property.

The Problem

Every week, Adriana writes backup snapshots of a production database to a cloud storage volume. Each snapshot uses 3.5% of the volume capacity. At the moment, 62% of the volume capacity is free.

If Adriana wrote 5 snapshots this week, how much free capacity remains on the volume?

  • a) 217 megabytes
  • b) 17.8%
  • c) 44.5%
  • d) 45%
Click to Reveal the Answer

Correct Answer: c) 44.5% ✅

Math Solution

Five snapshots at 3.5% of capacity each consume 5 × 3.5 = 17.5 of the free share, so the remaining free capacity is 62 − 17.5 = 44.5. Both figures stay in percent of the same volume, which is what makes the subtraction valid.

The volume loses 17.5 points of free capacity a week, so the free share reaches zero in under four weeks at this write rate.

Step-by-Step Breakdown

The following sequence shows how the final amount is derived:

  1. Capacity per snapshot: 3.5% of the volume
  2. Snapshots written: 5
  3. Distributivity of multiplication over addition: 5(3 + 0.5) = 5(3) + 5(0.5) = 15 + 2.5 = 17.5
  4. Substitution: free capacity remaining = 62 − 17.5
  5. Associativity of addition: 62 − 17.5 = (62 − 17) − 0.5 = 45 − 0.5 = 44.5
  6. Verification: 44.5 + 17.5 = 62, which returns the starting free share
  7. Conclusion: 44.5% of the volume capacity stays free

Solution With Named Properties

Mode. Compute.

Setup. Let f be the free capacity before this week's writes, u the capacity one snapshot consumes, n the number of snapshots written, and F the free capacity that remains. Each write removes u from the free capacity, so n writes remove nu. Therefore F = f − nu, with f = 62, u = 3.5 and n = 5. All quantities are percentages of the same volume.

Notation

  • f is the free capacity before the writes, 62 in percent.
  • u is the capacity one snapshot consumes, 3.5 in percent.
  • n is the number of snapshots written this week, 5.
  • nu is the total capacity the week's writes consume.
  • F is the free capacity remaining, the unknown, in percent.
  • ⇒ reads implies.

Step 1 — Distributivity of multiplication over addition

Property. Distributivity. x(y + z) = xy + xz.

Inference. nu = 5(3 + 0.5) = 5(3) + 5(0.5) = 15 + 2.5 = 17.5.

Step 2 — Substitution

Property. Substitution. x = y ⇒ x may replace y.

Inference. F = 62 − 17.5. From line 1.

Step 3 — Associativity of addition

Property. Associativity of addition. (x + y) + z = x + (y + z), so a subtraction may be split into parts.

Inference. 62 − 17.5 = (62 − 17) − 0.5 = 45 − 0.5 = 44.5.

Step 4 — Transitivity of equality

Property. Transitivity of equality. x = y and y = z ⇒ x = z.

Inference. F = 44.5. From lines 2 and 3.

Verification

F + nu = 44.5 + 17.5 = 62 = f. Both sides match.

Answer

F = 44.5, option c. About 44.5% of the volume capacity stays free after the five snapshots.

Option a is stated in megabytes. The problem fixes no total capacity, so that option cannot be evaluated by computation, only ruled out by unit mismatch.

Historical Background

Counting in hundredths is a fiscal habit before it is a mathematical one. Rome levied the centesima rerum venalium, a hundredth on goods sold at auction, and clerks learned to state a levy as so much per hundred rather than as a fraction of an unknown total.

Italian merchant houses of the fifteenth century carried the habit into ledgers, where interest, freight and losses were all quoted per hundred so that accounts of very different sizes could be compared on one page. The modern capacity dashboard inherits that convention, which is why a storage volume reports a share rather than a raw count of bytes.

Python Version

The script turns the weekly write pattern into a reusable capacity check, so the same function answers the question for any snapshot size, any write count and any starting free share.

def remaining_free_capacity(free_percent, percent_per_write, writes):
    """Return the free capacity left, in percent, after a batch of writes."""
    consumed = percent_per_write * writes
    return round(free_percent - consumed, 2)


def weeks_until_full(free_percent, percent_per_write, writes):
    """Return how many further weeks of writes the free share supports."""
    per_week = percent_per_write * writes
    return int(free_percent // per_week)


if __name__ == "__main__":
    free = 62.0
    per_write = 3.5
    writes = 5

    print(remaining_free_capacity(free, per_write, writes))
    print(weeks_until_full(free, per_write, writes))

Run it with python capacity.py. It prints 44.5, the free capacity in percent after this week, and 3, the number of further weeks the current free share supports at the same write rate.
